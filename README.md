# 星河游戏俱乐部管理系统

单俱乐部本地应用。Node.js 24 + 原生 ES Modules + SQLite，浏览器无需构建或在线字体资源。

## 启动

```powershell
node server.mjs
```

打开 http://127.0.0.1:4173/ 。开发时可使用 `node --watch server.mjs`。数据首次启动时写入 `data/club.sqlite`，后续启动会保留。默认仅监听本机。

### 正式环境启动

正式环境不会加载演示账号、示例订单或示例商品。复制 `.env.example`，设置 `NODE_ENV=production`、对外 HTTPS 来源 `CLUB_PUBLIC_ORIGIN`、独立持久化数据库 `CLUB_DATABASE`，以及首次启动用的管理员账号、强密码和名称；使用 `node --env-file=.env server.mjs` 启动，反向代理应自行按真实客户端 IP 做登录/注册限流，并将 Host 原样转发。Node 服务继续只监听 `127.0.0.1`，Cookie 会自动启用 `Secure`。

首次启动成功后可删除 `CLUB_ADMIN_PASSWORD`；已有正式数据库重启不再要求初始密码。正式数据库不能与演示库混用，启动时会拒绝迁移演示数据。

### 数据库备份与恢复

备份会在线读取 SQLite WAL、校验完整性并拒绝覆盖已有文件：

```powershell
node scripts/database.mjs backup
node scripts/database.mjs backup C:\data\club\club.sqlite C:\backup\club-2026-09-13.sqlite
node scripts/database.mjs restore C:\backup\club-2026-09-13.sqlite C:\data\club\club-restored.sqlite
```

恢复前请停止服务并使用全新目标路径；恢复会清除旧登录会话和统计缓存。备份目录已加入 `.gitignore`，不要把 SQLite 文件提交到代码仓库。

## 负责人首页

一级导航为首页、俱乐部配置、成员管理、客服管理、考官管理、售后管理、财务管理、订单管理。财务管理包含财务列表、抽佣配置、充值审核、资金流水和提现结算；订单管理包含订单、转单和派单列表。客服和打手继续使用各自的工作台，统计接口仅限最高负责人访问。

- 经营总数据展示已完成金额、完成笔数、下单用户人数。快照保存在 SQLite 中，每四小时更新，刷新页面不提前重算，并显示统计截止时间。
- 日经营数据可选单日；订单流水趋势可选起止日期，蓝线显示订单数，绿线显示 GMV，支持逐日明细。日数据、曲线和排名每五分钟刷新。
- 陪玩、下单用户、已完成订单三个榜单可独立按日期、游戏、Tag 和金额/笔数筛选排序，支持分页及关联订单明细；Tag 自动同步“特殊订单”服务名称，暂停服务仍保留查询入口。
- 日期按北京时间计算，包含结束日，单次最长 366 天。完成指标按完成时间统计；下单用户按创建时间去重，旧订单缺少客户 ID 时按老板称呼去重。多人订单在俱乐部总额中只计一次，陪玩榜每位成员展示参与订单的全额，不代表个人分成，不能相加作为俱乐部 GMV。
- 页面使用已有示例订单，不复制参考截图中的营业额。旧导入示例缺少完成时间时使用下单时间，真实订单缺少完成时间不纳入日期统计。

## 业务流程

“成员管理”展开为“俱乐部成员管理”和“俱乐部陪玩管理”。全体成员包括陪玩，设为陪玩后自动进入陪玩列表。非陪玩可设置为俱乐部会长（最高负责人）、俱乐部财务、俱乐部客服、俱乐部考官、俱乐部售后或普通成员。角色改变即撤销旧会话，服务端逐项限制数据与操作；三类业务人员会自动出现在对应管理页。

陪玩等级从高到低为明星、魔王、巅峰、金牌，只用于接单门槛。游戏与成员等级共同决定接单范围，高等级可接低等级订单，反向不允许；派单、直接接单、确认和开始服务均会校验。抽佣比例在财务管理中按游戏配置，多人订单按参与人数分摊，派单后锁定当时的游戏抽佣比例。等级不额外改变现有商品售价。

支持成员搜索、角色筛选、陪玩游戏与状态筛选、分页、批量增加游戏、冻结/解冻。冻结后禁止接新单和开始服务，已开始的服务仍可提交完单。取消陪玩身份需先结清订单、余额及提现，取消后保留普通成员身份。降低等级或删除游戏不得与待确认、待服务订单冲突。

老板下单 → 客服收到消息并邀请候选打手，同时符合条件的打手可自主报名 → 老板从候选名单选择 → 被选打手确认接单 → 开始服务 → 提交完单说明 → 客服或老板验收 → 分成入账 → 提现审核与打款。

### 跨账号自动同步与通知

登录后的首页、个人中心和各职责工作台每 3 秒同步一次共享业务数据；回到页面或网络恢复时立即尝试同步。用户下单后客服收到新订单通知，符合游戏和等级要求的打手同步在接单大厅看到订单；客服邀请和打手自主报名合并为候选名单。老板在“我的点单”选择后，被选打手收到确认接单通知，其他报名打手收到招募结束提示。接单、开始服务、提交完单、验收、转单、退款、聊天、充值与提现处理会同步给有权限的相关人员，订单、余额和收益仍以同一份服务端记录为准。

右下角“通知中心”保存本人未读通知，退出或服务重启后仍可查看；工作人员浏览个人首页时也能收到工作通知。通知按当前身份和订单归属再次校验，转出打手只保留移出提醒，不再接收后续服务详情。最近 100 条优先展示未读，标记后可继续处理更早的未读。通知是站内提醒，关闭网页后需重新打开才能查看。

自动更新保留当前页面、搜索筛选和正在编辑的表单；弹窗关闭后更新列表，订单详情会同步最新进度。多人同时处理同一订单时仍校验订单版本，避免重复派单或重复入账。不同角色联调请使用不同浏览器或独立浏览器配置；同一浏览器的标签页共享登录 Cookie，切换账号时旧页面会要求重新登录。

同步接口：`GET /api/sync?since=<revision>&context=personal|management`，返回当前账号 `userId`、版本号及本人通知；数据变化时附带对应工作区。`GET /api/notifications` 读取通知，`POST /api/notifications/read` 使用 `{ "ids": ["通知ID"] }` 标记本人通知已读。

- 老板订单进入待接单后，客服可在派单台邀请多位候选打手，其他符合游戏、等级和账号状态要求的打手也可看到订单，上线后自主报名；邀请和报名均不占单，最终由老板选择。多人服务按照下单时的人数快照校验，确认后才锁定分成。客服为已注册老板代下的订单同样需要老板选择；未关联登录账号的历史或线下代录订单保留原派单流程。
- 订单有版本检查，同一订单不能被重复选定；同一成员不能同时开始两笔服务。
- 派单校验人数、游戏状态、在线状态与分成总和；分成保留在订单中，后续改成员比例不影响已分配订单。
- 金额以整数分保存，按服务端商品定价；余额支付校验并扣减余额。
- 完单必须验收后才能入账；充值和验收都不能重复入账。
- 提现扣减可提现余额并冻结，驳回返还；押金低于 1,000 元、账号停用或已有待审核申请会拦截。
- 登录使用散列密码与 HttpOnly / SameSite Cookie，会话有效期 8 小时；每次接口请求都重新校验账号与角色。角色和订单归属由服务端决定。

## 当前范围

这是使用演示数据的本地可运行版本。会话页面支持用户与工作人员双向发送、独立未读状态、每 3 秒自动同步、内部跟进和 SLA 超时标记；尚未接入微信或支付宝外部消息渠道。当前“在线支付”实际是站内余额扣款，充值、线下退款和提现保留凭证、幂等和对账流水，但不会调用微信/支付宝或银行接口。要正式启用自动支付，必须先接入已签约的微信或支付宝商户网关，完成签名验签、回调幂等、订单关闭/超时、退款回调和日终对账；在这些配置完成前不得把余额扣款当作自动支付。经营汇总支持 CSV 导出，游戏与商品支持新增、编辑、上下架及引用保护；价格更改仅影响新订单。生产部署仍需配置 HTTPS、正式账号和密码管理、备份及真实支付/消息接口。完整后台链路见 [docs/后台管理链路.md](docs/后台管理链路.md)。

## 按全链路文档完善

- 管理首页提供派单、完单验收、退款、提现审核、待打款和会话六类待办；订单列表支持状态、游戏、关键字筛选并直接处理。
- 普通成员及工作人员的个人订单、钱包、消息与售后以本人顾客账户为范围；个人操作传入 context:personal 后仍由服务端重新核对归属。
- 用户确认完单与客服验收共用结算逻辑，退款同步调整收益，待验收订单部分退款后继续验收剩余金额，待线下打款计入冻结金额。
- 财务总览只使用实际提现和资金流水；历史示例批次不混入汇总。
- 登录与注册明确分开，移除固定演示验证码；未接入第三方支付或短信认证。
- 服务开始前可申请退款，审核期间暂停履约；全额退款结束订单，部分退款或驳回恢复原阶段。指定陪玩在扣款前校验人数、冻结与等级，长商品名及同名顾客均可正常购买。
